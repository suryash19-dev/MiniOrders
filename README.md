# MiniOrders - Mini Order Management API

A small .NET 8 backend for creating customers and orders and viewing them. The solution demonstrates a layered architecture, separated command and query services, EF Core Code First persistence, FluentValidation, repositories with a Unit of Work, and Swagger.

**Stack:** .NET 8 Web API · EF Core 8 · SQL Server · FluentValidation · AutoMapper · Swagger (Swashbuckle) · `ILogger<T>` · xUnit

## Project structure

```
MiniOrders.Api/             Controllers, requests, exception handler, Swagger, Program.cs
MiniOrders.Application/     Services, commands, validators, DTOs, mapping profiles, interfaces
MiniOrders.Domain/          Customer, CustomerProfile, Order, shared entity types
MiniOrders.Infrastructure/  EF Core DbContext, repositories, Unit of Work, migrations
MiniOrders.Tests/           xUnit tests for application, API actions, and persistence behavior
MiniOrders.sln
```

Dependencies point inward: `Api -> Application -> Domain`, while `Infrastructure -> Application` and `Infrastructure -> Domain`. The Application layer defines the repository and Unit of Work interfaces; Infrastructure provides their EF Core implementation.

## API endpoints

| Method | Route | Purpose | Status codes |
| --- | --- | --- | --- |
| `POST` | `/api/customers` | Create a customer | 201, 400 |
| `GET` | `/api/customers` | List customers with profiles and orders | 200 |
| `GET` | `/api/customers/{id}` | Get a customer with profile and orders | 200, 404 |
| `POST` | `/api/customers/{customerId}/orders` | Create an order for a customer | 201, 400, 404 |
| `GET` | `/api/customers/{customerId}/orders` | List a customer's orders | 200, 404 |
| `GET` | `/api/orders` | List all orders | 200 |

## Design approach

The application separates writes from reads with command and query services. Commands are validated before persistence; query services return DTOs rather than exposing domain entities. The controllers coordinate HTTP input and output, and the global exception handler maps validation failures and missing resources to Problem Details responses.

There is no mediator dependency: the controllers call the application services directly, keeping the request flow explicit for this small application. Entities are plain data classes; business validation is implemented in the Application layer rather than claimed as a rich domain model.

## Repository and Unit of Work

- `ICustomerRepository`, `IOrderRepository`, and `IUnitOfWork` are defined in `MiniOrders.Application/Abstractions`.
- Application services depend on `IUnitOfWork`. It provides both repositories and `SaveChangesAsync`.
- Infrastructure implements the repositories with EF Core. Read queries use `AsNoTracking`; list queries sort customers by name and orders newest-first.
- `SaveChangesAsync` delegates to EF Core's `DbContext.SaveChangesAsync`.

## Validation and error handling

- Customer name, address, and phone number are required. Their maximum lengths are 100, 200, and 20 characters respectively.
- Order customer ID and date are required; total amount must be greater than zero.
- Order creation checks that the customer exists before saving. Customer and order queries for missing resources raise `NotFoundException`.
- `GlobalExceptionHandler` returns 400 with property errors for `ValidationException`, 404 for `NotFoundException`, and a generic 500 response for unexpected exceptions. Unexpected exceptions are logged.

## Database

`MiniOrders.Infrastructure/Persistence/AppDbContext.cs` configures the model using EF Core's Fluent API:

- A customer has one required profile and may have multiple orders.
- Customer deletion cascades to its profile and orders.
- The profile's `CustomerId` is unique, enforcing one profile per customer.
- IDs are `Guid`s generated by the application (`ValueGeneratedNever`). Order totals use precision `(18, 2)`.
- Existing migrations are in `MiniOrders.Infrastructure/Migrations`.

## Getting started

**Prerequisites:** .NET 8 SDK and a SQL Server instance. The default connection string in `MiniOrders.Api/appsettings.json` targets SQL Server Express (`TI-LAP-1026\\SQLEXPRESS`); change it to match the SQL Server instance on your machine. The EF tool is needed only for database migration commands:

```powershell
dotnet tool install --global dotnet-ef
```

**Create/update the database** from the solution directory:

```powershell
dotnet ef database update --project MiniOrders.Infrastructure --startup-project MiniOrders.Api
```

**Add a migration** after changing the EF model:

```powershell
dotnet ef migrations add <Name> --project MiniOrders.Infrastructure --startup-project MiniOrders.Api --output-dir Migrations
```

**Run the API:**

```powershell
dotnet run --project MiniOrders.Api
```

The configured Development launch profile opens Swagger at `https://localhost:7188/swagger` (or `http://localhost:5097/swagger`). Swagger is enabled only in the Development environment.

**Sample requests:**

```http
POST /api/customers
Content-Type: application/json

{
  "name": "Asha Rao",
  "address": "12 MG Road, Bengaluru",
  "phoneNumber": "+91 9876543210"
}
```

```http
POST /api/customers/{customerId}/orders
Content-Type: application/json

{
  "orderDate": "2026-10-22T10:00:00Z",
  "totalAmount": 1499.50
}
```

## Tests

Run the complete test suite from the solution directory:

```powershell
dotnet test MiniOrders.sln
```

The `MiniOrders.Tests` project currently contains 32 passing tests covering:

- Customer command validation boundaries, creation, trimming, generated IDs, profile linkage, and customer queries.
- Order command validation, persistence for existing customers, missing-customer handling, and order queries.
- Repository filtering and ordering, loaded customer details, and EF model relationship and column constraints.
- Controller action results and global exception-handler responses for validation, not-found, and unexpected errors.

Persistence tests use EF Core's InMemory provider, so they do not exercise SQL Server-specific behavior, migrations against a live server, or the complete HTTP pipeline. A future integration-test layer could use SQL Server or a compatible test container and `WebApplicationFactory` for full HTTP coverage.
